# Runner economics experiment, 2026-09-07

## Decision

Do not switch production based on this experiment. The m8a.xlarge runner was faster with empty caches, but restored-cache work was nearly tied with GitHub. Its fresh-host startup and cache restore made warm jobs slower end to end. The tested network configuration also costs more than the compute.

Production Fargate was not changed. All temporary AWS infrastructure and credentials were removed after measurement.

## What ran

- Source snapshot `4dab568ac939063c488b2b9b280a05f674cb7094` on both providers.
- Full `bash ./dev/checks/backend with-api`, including the API tests, with Rust 1.98.0 and matching Cargo profile settings.
- AWS ECS Managed Instances, restricted to on-demand m8a.xlarge, 4 vCPU, 16 GiB host memory, 14 GiB task memory, and a configured 30 GiB data volume. PostgreSQL ran inside the pinned checks image.
- GitHub's actual standard public-repository `ubuntu-24.04` runner, observed as 4 logical CPUs and about 16 GiB memory. PostgreSQL 16 ran as a service container. This was not a paid larger runner or a private-repository 2-core runner.
- Three empty-cache samples and three restored-cache samples per provider. AWS also ran an eight-job simultaneous submission burst using restored caches. GitHub's three-job matrices were concurrent, but there was no matched eight-job GitHub burst.

All 20 final performance samples passed. AWS additionally passed its cache-seeding run. Each of the 14 measured AWS jobs had one attempt and a distinct ECS container-instance ID, including no host reuse between the cold, warm, and burst groups. The seed and preliminary failed setup also used different container-instance IDs.

One preliminary AWS setup attempt failed because the image did not contain `/usr/bin/time`. The measurement wrapper switched to Bash's built-in timing while keeping workload stderr separate, and both providers then measured the corrected source snapshot. That failure is not counted as a workload flake. It still consumed about 1.14 GB of NAT traffic and some compute. Superseded or cancelled GitHub runs are excluded from the final comparison.

## Performance

Seconds, shown as median / maximum. These are small samples, not credible p95 estimates.

| Provider and cache | Samples | Full workload | Submitted/created to result |
| --- | ---: | ---: | ---: |
| GitHub, cold | 3 | 416.83 / 418.47 | 447 / 447 |
| AWS, cold | 3 | 337.75 / 352.24 | 402 / 415 |
| GitHub, restored | 3 | 261.62 / 265.85 | 312 / 319 |
| AWS, restored | 3 | 253.49 / 258.45 | 347 / 354 |
| AWS, restored eight-job burst | 8 | 251.02 / 270.38 | 346.5 / 364 |

AWS cut median cold workload time by 19.0% and cold end-to-end time by 10.1%. Restored workload time improved only 3.1%, while end-to-end time was 11.2% slower. GitHub end-to-end starts at job creation, not the start of the earlier dependency matrix. Scope starts at run creation. Both include setup and completion overhead, but their surrounding services differ.

The burst did not produce retries or a large slowdown. Dispatcher logs show two groups of four provider-start calls roughly one second apart. The configured admission limit remained 20 and the provider-start limit remained four. Eight offered jobs do not prove behavior at the 20-job admission limit.

## Cache and network measurements

Every restored AWS sample hit both exact caches. The archives totaled 769,066,894 bytes, about 0.769 GB. The first warm sample took 25.27 seconds to prepare both caches. Its larger archive spent 13.76 seconds downloading and verifying, 3.05 seconds synchronizing files, and 6.53 seconds extracting. GitHub cache-restore steps took 11, 14, and 16 seconds.

| AWS cohort | Jobs | NAT bytes, both directions | Decimal GB per job |
| --- | ---: | ---: | ---: |
| Cold plus cache seed | 4 | 5,783,525,718 | 1.446 |
| Restored | 3 | 5,853,970,438 | 1.951 |
| Restored burst | 8 | 15,584,476,727 | 1.948 |

The combined warm/burst average was 1,948,949,742 bytes per job, or 1.815 GiB. These totals add `BytesInFromSource` and `BytesInFromDestination`, so forwarded bytes are not counted again using the corresponding output counters. The experiment had its own NAT gateway.

The checks image was 1,118,978,788 compressed bytes. Image size plus restored cache size explains most of the network traffic, although the NAT metrics do not attribute bytes to individual endpoints. There was no S3 gateway endpoint in the tested stack. Fresh hosts therefore repeatedly paid the network cost of image pulls.

Railway bucket downloads and S3 API operations are free. Payloads travel directly through presigned bucket URLs, not through a Railway service proxy, so Railway service-egress pricing does not apply to these cache downloads. AWS NAT processing still does. See [Railway bucket billing](https://docs.railway.com/storage-buckets/billing).

## Cost model, not a reconciled bill

The EC2 observer omitted `--include-managed-resources`. Its 305 inventory samples returned no hosts even while ECS recorded running tasks. Consequently, this experiment did **not** capture exact EC2 billed lifetimes, root/data-volume inventory, provisioned IOPS, or throughput. The query has been corrected for a future experiment, but that correction was not exercised against live hosts after teardown. AWS documents [managed-resource visibility](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-managed-instances.html). ECS task duration is not a substitute for billed instance lifetime.

The monthly figures below are a sensitivity model for repeatedly running this same commit with exact cache hits. They are not measured all-in invoice totals.

Inputs:

- The captured AWS Price List API returned $0.24344/hour for EC2 and $0.029208/hour for ECS management, totaling $0.272648 per host-hour. No Spot discount or Savings Plan is assumed. [ECS pricing](https://aws.amazon.com/ecs/managed-instances/pricing/).
- Measured 1.949 decimal GB per warm job, modeled at $0.045/GB NAT processing. Decimal GB is a conservative conversion; the raw bytes are preserved for invoice reconciliation.
- One NAT gateway and its public IPv4 address continuously available for 730 hours, totaling $36.50/month. The actual experiment's NAT was deleted, so that ongoing monthly charge was not left running. [VPC pricing](https://aws.amazon.com/vpc/pricing/).
- Half the jobs assumed to run across an availability-zone boundary from NAT, charged at a combined $0.02/GB for both endpoints. Actual placement was mixed; this is a planning assumption, not a per-job transfer invoice.
- Illustrative 34 GiB of baseline gp3 storage, consisting of the configured 30 GiB data disk and an **assumed**, unmeasured 4 GiB root disk, at $0.08/GiB-month. Extra provisioned performance is not included. [EBS pricing](https://aws.amazon.com/ebs/pricing/).
- One retained cache generation, rounded to 1 GB-month at Railway's $0.015 rate.

| Scenario | Variable cost/job | 500 jobs/month | 10,000 jobs/month |
| --- | ---: | ---: | ---: |
| AWS, 6.5-minute billed host assumption | $0.1371 | $105.08 | $1,407.84 |
| AWS, 8-minute billed host assumption | $0.1440 | $108.54 | $1,476.94 |
| AWS, 10-minute billed host assumption | $0.1533 | $113.14 | $1,569.06 |
| Actual GitHub standard public runner, runner charges | $0 | $0 | $0 |
| GitHub paid 4-core price proxy, observed 5–6 rounded warm minutes | $0.060–0.072 | $30–36 | $600–720 |

GitHub's public standard runners are [free](https://docs.github.com/en/billing/concepts/product-billing/github-actions). The paid 4-core row applies its [$0.012/minute rate](https://docs.github.com/en/billing/reference/actions-runner-pricing) to the observed duration only. It is not a measured paid-runner result and excludes the required plan cost. The public runner measured here cannot establish runtime on GitHub's private 2-core tier. Cold jobs used eight rounded runner minutes, giving a paid 4-core price proxy of $0.096/job.

The AWS eight-minute scenario has about $0.0364 compute, $0.0005 assumed disk, $0.0877 NAT processing, and $0.0195 assumed cross-zone transfer per job. Even the measured traffic's modeled NAT processing alone exceeds the six-minute paid GitHub proxy.

Real CI usually changes the source. These cache keys include source identity, and exact-hit runs skip archive uploads. Uploading another archive set of the same 0.769 GB would add approximately $0.104/job in NAT processing and AWS internet egress at $0.09/GB, before cross-zone transfer and any shared free-egress allowance. At the assumed cross-zone mix it adds about $0.112/job, or roughly $56 / $1,115 for 500 / 10,000 such uploads. This is a transfer-only estimate, not a measured changed-commit run. Upload time, longer host life, rebuild work, and retained cache generations can add more.

The table excludes shared Railway API/worker/cache-service compute, CloudWatch metrics/logs, Secrets Manager, additional retained cache generations, ECR storage allocation, retries, and changing-cache uploads. It also excludes discounts, taxes, and account-level free allowances. Those omissions and the missing EC2/EBS measurements prevent an all-in cost claim.

## Follow-up worth testing

An S3 gateway endpoint should remove most ECR image-layer traffic from NAT without reusing hosts. AWS lists no hourly or processing charge for that endpoint type. This was not implemented or measured here. Cache transfer over the public network, cross-zone placement, startup latency, and exact host/disk billing would still need measurement. Keep the fresh-host isolation requirement.
